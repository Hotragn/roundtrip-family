# Decisions

Each entry: the decision, then the reason in one line. Newest last.

## Setup

1. **The plan lives at docs/plan.md and the brand files at brand/.** CLAUDE.md, docs/brand.md and the playbook all point to those paths; the files arrived as docs/roundtrip-plan.md and "brand assets/".
2. **CLAUDE.md was created from playbook section 2.** It didn't exist yet. Changes from the playbook text: where development runs, the .env line the builder asked for, the outbound registry path, and a writing section.
3. **"pstack" means the gstack skill suite.** No skill with that name is installed; gstack is the installed engineering suite (plan reviews, code review, QA). Superpowers and Ponytail aren't installed either.
4. **TypeScript is pinned to 6.0.3.** TypeScript 7 is the new native compiler, and Next.js type checking and the test tooling still use the JavaScript compiler API.
5. **Code is written and tested in this checkout; speech models and the Temporal worker run in the Codespace.** This machine is Windows on ARM64, where the speech libraries and Temporal's native worker are unreliable or missing; the Codespace is Linux x64 with 16 GB.
6. **Shared code goes in packages/core.** The web app, the agent and the workflows all need the same schemas, country data, outbound registry and diary crypto, and plan section 14 has no shared package.
7. **Email is sent only when DEMO_ALERT_EMAIL is a valid address.** The current value doesn't pass a format check; the code checks it at runtime, sends nothing otherwise, and logs that it skipped.
8. **Commits carry no co-author trailer from here on.** The builder's goal asks for none.

## M1 Foundations

9. **Gemma's thinking is turned off with `chat_template_kwargs.enable_thinking=false`.** With thinking on, a 200-token reply came back empty because reasoning used every token; with it off the same Telugu sentence took 1.3 s and 36 tokens (live probe, 2026-10-05).
10. **Embeddings come from EmbeddingGemma-300m on Workers AI, not a model run in the Codespace.** It is an open multilingual model, and the hosted app can embed new events with it; a Codespace-only model couldn't. Measured: an English and a Telugu description of the same event score 0.845 cosine, an unrelated listing 0.281.
11. **Atlas Vector Search is used directly.** The free M0 cluster accepted the vector index; `similar()` still falls back to cosine in code while an index is building.
12. **Demo content is read from files; live state goes to MongoDB.** Seeded demo weeks, cards and audio ship in data/demo/, so CI and the offline app work without Atlas; approvals, check-ins and diary entries use Atlas.
13. **Python projects use 3.12.** numpy 2.5 needs 3.12; tabpfn-client 0.6.1 caps pandas at 2.3.3, so pandas is pinned to that range.
14. **Biome lints and formats.** Next.js 16 removed `next lint`, and one tool for both jobs keeps dependencies few. Persona, docs and brand files are excluded so they stay exactly as written.
15. **Playwright drives the installed Chrome locally and its own Chromium in CI.** This machine is Windows on ARM64.
16. **The Fremont home area is Mowry Ave & Fremont Blvd.** It is a real intersection next to the Walgreens at 2600 Mowry Ave, and the Safeway at 39100 Argonaut Way is about a 20-minute walk away, which matches the persona's "walk to Safeway, too hot, no shade" outing. OpenStreetMap data (Overpass) confirmed both stores.
17. **The Munich household lives near U-Bahn Neuperlach Zentrum,** and both demo contact numbers come from ranges reserved for fiction (NANPA 555-01xx, Bundesnetzagentur (0)89 99998 xxx).
18. **Emergency numbers were checked on official pages:** 911.gov for the US and the BBK (Federal Office of Civil Protection) for Germany's 112 and 110.
19. **Privacy is enforced in code, not only in the table.** Every outbound call declares a data class, the registry lists which classes each route may carry, and personal data never reaches a hosted route. The persona's ratings are synthetic, so they may go to the hosted TabPFN; a real family's ratings would need TabPFN run locally.
20. **OpenRouter's free Gemma endpoints returned 429 "rate-limited upstream" during setup.** The helper backs off and moves on, and replays saved outputs when every host is busy.

## M2 Intelligence

21. **Events come from SerpApi's `engine=google` events block.** The dedicated `google_events` engine answered "Unsupported" for this account on 2026-10-05; SerpApi documents the events block of Google search as the alternative.
22. **Only billed searches count against SERPAPI_MAX_SEARCHES.** SerpApi doesn't bill failed requests; the account API confirmed 14 billed searches when the first counter said 23.
23. **Event understanding uses a v2 prompt that spells out each field.** The model-check prompt misread "community hall" as outdoor and "all ages" as unsuitable; v2 scored 100% on language match over 40 synthetic listings in its first round.
24. **Places must be the expected venue type and have at least 10 reviews.** Sorting by distance alone picked a library foundation, a county administration office and social-services offices.
25. **Event venues are geocoded with OpenStreetMap Nominatim.** Listings give a venue and town but no coordinates; Nominatim is free and its policy allows light, cached use.
26. **Reason chips come from grouped leave-one-feature-out on expected enjoyment.** tabpfn-client has no attribution method. Grouping the trip, timing and weather features and refitting only the regressor, in parallel, cut a ranking from about 150 s to under 40 s. Chips are dropped when they can't be true: weather for an indoor place, or "like the outings they enjoyed" for a kind of outing they've never done.
27. **Every candidate is scored as a solo outing.** In the persona's history every 5-star outing had the adult child along, so scoring weekend family slots with that flag ranked a Saturday market first for that reason alone.
28. **Code finds, schedules and scores; the Mastra agent chooses and explains.** With Mastra's structured-output option Gemma skipped the tools and invented candidate ids. The agent now gets the real candidates with each parent's slot and TabPFN score, answers in JSON that code parses, and every choice is validated against the candidate list. Fallbacks fill any week to two or three options down the ladder.
29. **suggestTrialRun is not one of the agent's tools.** Gemma's arguments for it repeatedly failed to parse; first rides are decided by code from the routes already ridden.
30. **Model choices.** Planner: Gemma 4 26B A4B on Cloudflare (script intact 20/20, names kept in English, under a second, free). Card-writer base: Qwen3.5-4B, the weakest Telugu writer in the check, so the fine-tune has the most to show; Qwen3.5-9B is the fallback. Model-check judge: Kimi-K2.6, a different family from Gemma and Qwen. The teacher is chosen by a small card pilot in M5.
31. **The stop countdown comes from SerpApi directions.** Transit legs list every intermediate stop, so the stop just before theirs needs no extra data source. SerpApi reads `depart_at` as UTC wall-clock time, so local times are encoded that way.
32. **Every external call is recorded.** SerpApi responses, Gemma answers, TabPFN predictions, ranker responses, forecasts and geocodes are saved as fixtures, so CI and the hosted demo replay them without calling anything.

## M3 Parents' app

33. **next-intl runs without its build plugin.** The plugin loads @swc/core's native binding, which isn't built for Windows on ARM64. The parents' app gets its Telugu messages from a client provider, which also keeps its pages static and offline.
34. **Each parent has their own prerendered page, and views change with the history API.** /parents/fremont-demo/p_sarala carries that parent's week in its HTML, so the ticket shows before any script runs, and ?v= view changes never need the server. A single client-rendered /parents page scored 72 on Lighthouse with a 5.3 s LCP; this one scores 87 to 90.
35. **The parents' app keeps its light palette in dark mode.** Parents read it outdoors in daylight and every line sits on a white panel. axe runs in both schemes.
36. **The ticket's place photo is a 96 px thumbnail beside the times.** A full-width photo pushed Listen and Directions below a phone's first screen and was the slowest thing on the page. Photos are requested at the size shown, as WebP at quality 60 (18 KB instead of 317 KB), retried once at the original size and hidden if both fail.
37. **Fonts are self-hosted with next/font/local.** The seven files are Google Fonts' latin and telugu subsets of Hind and Hind Guntur, each face declares only its own characters, and Hind comes first in every stack. With next/font/google, digits and names inside Telugu text pulled in Hind Guntur's three Latin files.
38. **Styles are inlined into the HTML** (Next.js `inlineCss`): no render-blocking request, and the page cached for offline carries its own styles.
39. **The service worker stores one copy of each page without its query, warms itself from what the page loaded, never reloads on reconnect, and is off in development.** Reloading when the phone reconnects would cut off a recording; the outbox sends instead. In development it served stale chunks.
40. **A transit leg's vehicle comes from Google's transit icon** (bus2.svg, de-sbahn.svg, de-metro.svg), then the line name and operator, never the headsign.
41. **No screen branches on a language code.** Language names come from the language table (what a Telugu speaker calls English or German), speech tags from the table or the household's country, and the help card's and walking driver card's lines from the household's local phrases.
42. **esbuild is a dependency of apps/web.** Serwist's Turbopack route bundles the service worker with it (an optional peer dependency), at build time and in development.
43. **The visitor session cookie is Secure whenever the request came over HTTPS** (Render's proxy sets x-forwarded-proto), and outbox sends run one at a time so a phone never starts two sessions at once.

## M4 Dashboard

44. **Every slot fits the place's listed opening hours.** They arrive while it's open and leave ten minutes before it closes; a visit shortens to about 60% of its usual length when the place closes sooner, or the slot moves. The first plan sent a parent to a temple that opens only on Sundays and to two shops before they opened. Hours come from the Google Maps listings already saved, so this cost no searches.
45. **The week builder re-checks the hours with the real route** and stops with an error if a real trip arrives before opening or too close to closing. The planner schedules with a straight-line estimate, and one estimate was half the real trip.
46. **Two parents never go to two places of the same kind on the same day.** The second one moves to another free day. The re-plan had sent one parent by bus to an Indian grocery while the other walked to a different one at the same hour.
47. **Each parent gets at least one outing on their own when one is feasible.** Getting out on weekdays is the point; one Gemma answer gave the father only a weekend outing with the adult child.
48. **A reason that only repeats a chip, or names another kind of place, is replaced with a line from their own ratings** ("She gave her last 5 temple visits 5 of 5."). Gemma echoed "Like the temple outings they enjoyed" and once called a farmers market a walk in the park.
49. **Reason chips name the kind of place properly and say the household's local language** ("Indian grocery", "No German needed"). The ranker labels chips without knowing the household.
50. **Walks with no saved directions use an OpenStreetMap walking route (OSRM foot profile) at 4.5 km/h.** Walking doesn't depend on timetables, and it kept SerpApi at 39 of 40 searches.
51. **The week board has a column for each weekday and one for the weekend.** Seven equal columns made every card too narrow to read at 1440 px. Drag and drop is dnd-kit (pointer and keyboard sensors); a move is checked on the client and again on the server against the days they're on their own and the place's hours.
52. **A visitor's approvals, swaps and moves live in their session for a day, and their parents' phones in the same browser pick them up** (/parents/api/changes). The approve toast promises the ticket is on the phone; now it is. A moved ticket's Telugu day name is rewritten to the new day.
53. **MapLibre GL 6 with OpenFreeMap's positron style, restyled in brand tones.** No key and no billing. Its worker is copied to public/maplibre/<version>/ before dev and build, because MapLibre looks for its worker next to its own script and a bundled chunk has none there.
54. **New libraries, one job each:** TanStack Query (the board's changes, with optimistic updates), TanStack Table v9 (the privacy table's sorting), React Hook Form with the Zod resolver (safety settings and setup), Sonner (toasts), dnd-kit (drag and drop), MapLibre GL (route maps). vaul and @dnd-kit/sortable were installed and then removed, unused.
55. **The themed scroll track replaces the scrollbar only on precise pointers.** Rail: the baked track down the right edge with the train's nose as the handle. Sea: a slim waterline dock along the bottom with the ferry, so the ferry never sits over text. Touch screens keep native scrolling with a thin progress line. All of it is aria-hidden; native scrolling stays the accessible way.
56. **A place photo shows only once it has loaded.** Google's image service intermittently refuses headless browsers; the tile underneath shows a sign for the kind of place, and a failed sized copy retries the original once.
57. **People and places shows the exact sentence the planner is told about each person**, from the same function the planner uses. Forgetting someone stops them being described to the planner (per session in the demo).
58. **Their week shows only what the phones report:** "I'm home", and the face picked for "How was it?". Voice notes stay on the phone in the demo; diary entries stay private unless shared.
59. **The Languages screen reads its status from the build's own outputs:** which writer made this week's cards and how many pass the rubric, and whether any audio clips exist. A language record says what a model supports; the screen says what this demo actually does.
60. **Setup asks only for first names, the nearest stop and one contact number,** and lists only countries whose emergency number has been checked against an official page.
61. **A persona note was reworded.** "Said he felt stupid" became "couldn't ask for what he needed", because the product never describes the parents as helpless or pitiable.
62. **TabPFN's free daily pool ran out while re-planning ten weeks after these changes**; the last three were planned after its 00:00 UTC reset. Only changed feature rows are sent, so later re-plans cost little.

## M5 Diary and voice

63. **Diary entries are encrypted on the family's server with each parent's own key before they're stored** (AES-256-GCM, the key derived per parent by HKDF, the entry and parent ids bound in so ciphertext can't be moved). The phone keeps its own copy, and its outbox sends each entry's latest state when it's back on home Wi-Fi, so a share tapped offline after a save goes out once.
64. **Only shared entries are ever decrypted, and only for Shared with you.** Private entries never leave the diary module, and a recording plays on the dashboard only while its entry is shared.
65. **Without DIARY_ENCRYPTION_KEY, development and tests use a random key for that process, and production refuses to store entries** (the phone keeps them). The key is missing from .env; the Render deploy gets a generated one in M7, and the CI end-to-end job generates a throwaway key per run.
66. **The demo's synthetic entries start on each parent's phone the first time their diary opens,** and the shared ones show on the dashboard. What a visitor shares, unshares, writes or deletes overrides them in that visitor's session.
67. **A diary page's place in the memory book travels with the entry,** so the pages a parent shares and puts in the book appear in their child's copy. Outing tickets chosen for the book stay on the phone.
68. **Photos stay on the phone in the demo.** Only words, feeling words and recordings sync.
69. **The voice router picks each voice by language:** Indic Parler-TTS for Indian languages and MMS-TTS otherwise, ElevenLabs only when asked for, with a key, within ELEVENLABS_MAX_CHARS and for a language it lists, so every language still gets audio. Saved clips are found by sha256 of the language and the exact text.
70. **Shared with you uses the home theme:** warm paper, no landscape band and native scrolling, with the memory book pages in the light palette in both schemes, like the printout.

## M5 Speech

71. **Telugu speaks with MMS-TTS Telugu (facebook/mms-tts-tel) and listens with MMS speech recognition (facebook/mms-1b-all, Telugu adapter), not Indic Parler-TTS and IndicConformer.** Both AI4Bharat repositories answered 403 "not in the authorized list" for the builder's Hugging Face token on 6 October, and the plan names MMS as the alternative. The code tries the AI4Bharat models first and moves to them by itself once access works.
72. **A text front end writes out what the voices can't read** (speech/speech/spoken.py): times with the part of the day (08:30కి becomes ఉదయం ఎనిమిదిన్నరకి), other numbers as Telugu words, and English or German names in Telugu letters from speech/speech/te_names.json, with letter rules and a warning for names it doesn't know. MMS-TTS Telugu's vocabulary has no digits or Latin letters, so it would skip the time, the bus and the place, the parts a parent needs most.
73. **Bus and train line numbers are read digit by digit** (Bus 211 becomes బస్ రెండు ఒకటి ఒకటి). That's how the number is printed on the front of the bus.
74. **The character error rate is measured against that spoken form, with reference and transcript both through cer.normalize, which now also drops zero-width joiners.** A listening model can't be expected to type "08:30" or a name in Latin letters, and Telugu's invisible joiner (బాత్‌రూమ్) changes only how a word is drawn.
75. **Cards are voiced sentence by sentence with 0.45 s pauses (0.2 s at commas), at MMS speaking rate 0.9 (0.85 for practice phrases), with a fixed seed per clip from its key.** MMS-TTS ignores punctuation, older listeners need the pauses, practice phrases are meant to be repeated, and a re-run should give the same file.
76. **Clips are mono MP3 at 48 kbps and 24 kHz, normalized in two passes to -16 LUFS with a -1.5 dBTP ceiling, with 0.15 s of silence first.** Any phone plays it, and some phones clip the first moment of playback.
77. **Each model runs in its own worker process, and its peak memory is that process's maximum resident set size.** A fair figure per model. Models download only the files they load into a cache under /tmp, deleted after each model (mms-1b-all is 29 GB in full; the weights and three adapters it needs are 3.9 GB).
78. **A clip is up to date when its file exists and the manifest says the model now chosen for its language made it.** Clips for texts that are gone are pruned, and clips made by other models (an ElevenLabs demo clip, say) are never re-voiced or pruned. Re-running after the tuned writer changes the cards re-voices only what changed.
79. **The manifest keeps exactly the agreed fields; evaluation detail goes to data/demo/audio/transcripts.json and time and memory to data/demo/audio/runs.json.** The web app and the voice router read the manifest, and the same text voiced in two places is one clip named by its first source.
80. **PyTorch comes from its CPU index on Linux, and imageio-ffmpeg is the one new dependency.** The previous lock pulled 14 CUDA packages and triton, several GB the Codespace can't use; imageio-ffmpeg supplies an ffmpeg binary for loudness normalization and MP3 when the system has none.
81. **The Codespace was rebuilt once and then left alone.** The rebuild failed in the sshd feature (a Yarn apt key), and the fix belongs in .devcontainer/, outside speech/ (docs/blocked.md).
82. **The synthetic diary voice clips are in the round trip, scored like every other clip.** The score measures the speech models on synthetic text, standing in for the parents' recordings as the build plan says; a real entry would never be scored (CLAUDE.md, privacy rules).

## M5 Card writer

83. **The card writer's teacher is Qwen3.5-397B-A17B.** In a 20-outing pilot its drafts got Gemma's tone 4 or 5 on all 20 with no unsupported facts, it beat Qwen3.6-35B-A3B 12 to 3 in order-swapped pairs and tied Kimi-K2.6 7 to 7, at $0.0023 a draft. It shares the student's tokenizer, and choosing it leaves Kimi free to judge.
84. **The teacher's fixed prompt is docs/card-style.md plus a short list of the code checks.** With the style guide alone all four teachers failed the checks on 14 to 17 of 20 first drafts (no మీరు form, the bus's direction in English, 12-hour times); with the list they failed 8 to 11. The prompt never changes, so 89% of the teacher's prompt tokens were cache hits.
85. **The student learns by prompt distillation: the facts prompt alone, answered with the kept card.** It is the plan's recipe, keeps each example near 290 tokens and the app's calls near 190 prompt tokens. The base model is evaluated with the style guide as its prompt, its strongest form.
86. **The held-out set is 40 outings at venues and events that never appear in training,** stratified by area, kind of trip and parent, as the M5 brief asked (the plan said 50). This week's demo venues stay in training.
87. **The gate's Gemma judge checks facts as well as tone.** A draft needs tone 4 or 5 and nothing the outing doesn't support; the code checks can't catch a wrong day or swapped stops.
88. **Pairs with a Gemma-written card are judged again by Kimi-K2.6.** Gemma may favor its own writing, and Kimi wrote none of the cards. Its calls go through the same Tinker client, spend cap and cache.
89. **The training run saved sampler weights after each epoch, and adapter.json points at the lowest validation loss** (epoch 3, 0.111 on 16 held-back examples). Still one run; epochs 1 and 2 are unused.
90. **The Tinker writer regenerates the way the Gemma writer does:** one retry that sends back the failing draft with its failures listed, so the evaluation compares models, not retry policies. A card from the trained adapter has writer kind "tinker_lora" and one from an untuned base model "tinker_base", the kinds the card schema already had; the model field names the checkpoint.
91. **tinker-cookbook 0.5.7, with tml-renderers skipped on Windows.** The lock had tinker-cookbook 0.1.0, which has no Qwen3.5 renderers or weights module; tml-renderers ships no Windows wheels, and only Inkling's renderers need it.
92. **Telugu cards come from the tuned writer, held to the training data's gate, with Gemma writing any card that fails it.** The plan gives a language its tuned writer once the pipeline has run for it, and the tuned writer passed more code checks (98% against 85%) with no invented text; the judges split (Gemma preferred its own cards 20 to 8, Kimi preferred the tuned ones 14 to 12 with 14 ties, docs/finetune-results.md). Reading this week's ten tuned cards found two wrong words and two that left out the walk from the stop, so every card now also needs Gemma's tone of 4 or 5 with facts that hold and, for a walk of five minutes or more, its minutes (agent/src/cards/gated-writer.ts). The tuned writer wrote 7 of the 10 cards.
93. **The direction a line runs toward is an allowed name on a card, and trains keep their own names.** Without the headsign no writer could say which way to ride; build-week had called the U5 "Bus U5".

## M7 Finish

94. **Sentry through @sentry/nextjs, on the server only.** It is the SDK Sentry documents for Next.js and reports request errors through the instrumentation hook; nothing is added to the pages, so the parents' phones load no extra script. Events lose request bodies, headers, cookies, query strings, user and breadcrumbs, messages are scrubbed of emails, phone numbers and the demo families' names, and it runs only on Render with SENTRY_DSN set.
95. **The planner's spans follow Sentry's AI agent conventions and carry names, models and counts only.** A run is "invoke_agent roundtrip-planner", each Gemma call "chat gemma-4" with its host, model, tokens and failed attempts, each tool "execute_tool <name>", and TabPFN "rank with TabPFN"; Sentry's own fields for messages, tool arguments and results stay unset, so no prompt or family detail leaves. The agent package defines the span hook and the web app plugs Sentry into it at startup, so the agent needs no Sentry dependency.
96. **Every "Plan the coming week" run is traced, and a tenth of other requests.** Re-plans are rate-limited to forty a day, so tracing all of them stays inside Sentry's free plan and makes each run inspectable.

## M6 Temporal, email, safety

97. **The workflows package uses Temporal's TypeScript SDK 1.24.0 (@temporalio/client, worker and workflow) with @temporalio/testing for its tests, and no other new dependency.** Temporal is the plan's workflow engine; its native worker has no Windows ARM64 build, so the worker, the durability run and the workflow tests run in the Codespace and in CI on Linux, and the tests skip on this machine with a message saying so.
98. **weekPlan replays the saved plan for the demo households onto the week being planned.** data/demo/weeks/ (the tickets) and data/demo/plans/ (the swap options) keep their days and times, placed on the coming Monday to Sunday in the household's time zone; planning live on every run would spend searches and Gemma calls.
99. **AgentMail over fetch through the privacy guard, not its SDK.** Five REST calls cover the email layer, every one goes through outboundFetch on the agentmail route, and no dependency is added.
100. **The webhook's Svix signature is checked by hand with node:crypto, following Svix's manual steps.** apps/web gets no new dependency in M6, and the test checks the code against Svix's published example.
101. **One inbox, found by client id "roundtrip-family" or display name "Roundtrip" and created only when neither exists, with sends capped at 300 a month.** The free tier allows 3 inboxes and 3,000 emails a month; a family's week needs a handful.
102. **DEMO_ALERT_EMAIL must be one plain address (no display name, no second recipient, no spaces or line breaks, a letter-only top-level domain), and every email is refused if it contains a phone number, a street address or an email address.** It is the only gate before a send, and emails carry first names and outing details only; places appear by name, never by street address.
103. **Workflow history holds ids, times and choices; first names and places are read inside the activities when an email is written.** The Temporal server is our own, but its history sits in a file; this keeps names out of workflow state.
104. **Reply rules: "yes" or "approve all" approves everything, naming outings to approve leaves out the rest, naming only outings to skip approves the rest, "swap N" brings the planner's next option for N and asks about the week again, and anything else gets a short reply asking again.** They are the dashboard's approve, skip and swap in words, and nothing is guessed.
105. **The reply reader reads only the first lines that look like an answer, with a closed vocabulary, and stops at quoted text and sign-offs.** A signature or a question ("Can we move 2 to Tuesday?") must never read as an approval.
106. **With no answer by an hour before the first outing leaves, nothing is set up that week.** An outing the adult child never approved shouldn't start; the planning email says when the answer is due.
107. **Outings with the adult child get no safety timer, and neither does an approved outing whose return has already passed.** An alert to the person who is with them is noise, and a timer for a past outing would alert at once.
108. **A safety timer starts when the week is approved, as a child that weekPlan abandons, not at departure.** Its deadline is the expected return plus the buffer either way, a check-in may come any time after approval, and the timer outlives weekPlan's weekly continue-as-new.
109. **The alert is due nudgeWaitMinutes after the nudge was due, not after the nudge was recorded.** A nudge delayed by a worker that was down must not push the alert later.
110. **After an alert, outingSafety keeps listening for "I'm home" for 12 hours and then sends a short "is home" email.** The adult child shouldn't be left worrying once the parent is back.
111. **trialRun books the first ride together on the household's next weekend day (trialRunDays), at the outing's own time when it falls between 09:00 and 16:00 and otherwise at 10:00, and marks the route solo-ready only once the ride is confirmed with a rode signal.** A route must not become solo-ready on a guess; unconfirmed, it offers the next weekend once more and then stops.
112. **weekPlan is one long-running workflow per household, week-plan-<household>, that sends the weekly summary and continues as new every Sunday at 18:00.** The plan says it runs every Sunday at 6 pm, and one id means the dashboard and email replies always reach the current week, with no Temporal schedule to manage.
113. **The weekly summary lists the approved outings with what the phone reported and the faces picked, and goes out only when something was approved.** Faces arrive by a howWasIt signal, which the reply route doesn't send yet (left to the main session, outside M6's files).
114. **The web app and the email listener signal Temporal over its HTTP API, sending full json/plain payloads.** The web app can't add the SDK, and in a probe against Server 1.32.0 the HTTP API's JSON shorthand turned an empty list into null; the workflow also reads a null list as empty.
115. **A check-in that can't reach its safety timer answers 503 so the phone sends it again; a timer that doesn't exist answers as before.** A lost "I'm home" would mean a false alert.
116. **The Temporal dev server is an outbound route (localhost, anonymized and synthetic, runtime), and temporal.download a build route.** The code talks to the server over the network, and the CLI and the test server are downloaded from temporal.download.
117. **Each workflow test gets its own time-skipping test server.** On a shared one, a child left running after its worker stopped held the clock still, and every later test timed out.
118. **The durability run starts its own dev server on ports 7299 and 7298 with a file database in a temp directory, prebuilds the workflow bundle, and kills the worker 26 s before the alert.** It touches nothing else in the Codespace, the restarted worker is ready in about a second, and a task sent to a dead worker's sticky queue can wait up to 10 s, which would measure that timeout instead of the timer.
119. **The durability run in the Codespace used a scratch clone of main with the uncommitted M6 files copied in.** The shared checkout there stays clean for the jobs that use it.
120. **Emails for a household that isn't synthetic are marked personal, so the privacy guard refuses them.** They carry first names, AgentMail is a hosted service, and the registry never lets personal data reach one; family mode needs a decision on the agentmail route (or a mail server the family runs) before real alerts can go out.
121. **Styles in one cached file again, not inlined.** Next's inlineCss put the 96 KB stylesheet in each page's HTML and twice more in its page data, so a parents' page was 334 KB before compression.
